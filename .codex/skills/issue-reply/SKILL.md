# 回复 issue

从已核对的远端、issue URL 或用户提供的信息确定仓库。需要核对本地实现或配置事实时，按根目录 `AGENTS.md` 定位实际源码与配置。公开回复使用主题内容的实际语言。

检索和发布使用平台实际可用的连接器或 CLI。GitHub 可使用 `gh issue view`、`gh issue list --search` 与 `gh issue comment`，仓库事实和会话已有信息直接复用。

## 执行流程

1. 有编号或 URL 时，查询标题、正文、状态与相关回复，核对仓库和主题。
2. 编号缺失时，整理会话已有的主题、关键词、对方原话和相关功能；线索齐全后自动检索对应仓库，必要线索待补齐时向用户询问。
3. 多个候选难以区分时，列出编号、标题、URL 与匹配依据，请用户选择；明确目标后阅读完整讨论。
4. 按下列草稿要求整理完整回复与附件，核对引用事实和公开内容。
5. 发布前展示目标仓库、issue 编号、标题、URL、回复语言与完整草稿，核对用户授权。会话中已明确要求向该主题回复且内容符合指定意图时，沿用授权；仅要求调查或准备草稿时，先取得发布确认。
6. 目标或回复意图超出已有授权时，说明本技能要求“发布前确认目标 issue 与完整回复草稿”，展示待发布内容并等待确认。
7. 授权覆盖本次目标与内容后，通过实际回复接口发布；使用 GitHub CLI 时，保存完整 UTF-8 正文并调用 `gh issue comment <编号> --repo <仓库> --body-file <草稿文件>`，保留实际换行。
8. 接口报错或发布结果待确认时，先查询回复是否已经生成，再按实际状态决定后续操作，避免重复发布。

## 草稿要求

- 根据主题正文和本次需要回应的内容判断语言，代码与日志作为技术材料处理。
- 先回应对方关心的问题，再说明实际结论、进展或所需复现信息。
- 态度友好、表达具体；遇到攻击式回复时承认对方的困扰，再把讨论引向事实、复现和解决办法。
- 优先说明能做什么、已完成什么和下一步；必要的纠错与失败事实直接说明。
- 公开内容保留问题所需的复现、结论和仓库相对路径。隐私、凭据、测试账号、设备标识和本机独特路径在草稿及附件中清理或脱敏后再使用。
- 版本、链接、技术判断与进度依据实际讨论和仓库事实填写；区分已验证事实、可能原因和仍需补充的证据。

## 完成与维护

核对实际发布状态及返回的回复 URL，确认回复对应目标仓库和 issue，并报告实际结果。

`.codex/skills` 为主源，修改后同步到 `.claude/skills`，检查文件集合与字节一致；已有镜像存在独立改动时先核对差异。
