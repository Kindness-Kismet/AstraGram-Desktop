# 拉取请求

默认 PR 流程为 `feature/<名称>` / `fix/<名称>` → `beta` → `main`：

- 功能分支的 PR 默认以 `beta` 为目标，先在 `beta` 集成和验证。
- `beta` 负责向 `main` 提交 PR，将已验证的改动合入正式发布分支。

用户明确指定其他目标分支时按指定值执行，准备前核对来源分支和目标分支。

PR 标题和正文必须全部使用英文；对用户的对话回复继续使用简体中文。

PR 正文直观、简洁地说明两个版本之间的最终变化，适当润色，让读者容易看懂新增、改善和修复了什么。
发布 PR 先核对基准版本和目标版本，在开头写明版本范围；功能 PR 按实际分支差异描述，不编造版本号。

按功能合并相关改动，省略已被回退或替代的中间方案。标题使用英文祈使句，正文用简短段落或条目，避免实现流水账。
测试细节、构建与审查结果、用户的本地要求、对话过程及后续工作安排保留在提交说明或本地记录中，不写进 PR 正文。

以下内容供准备和审查时内部核对，不作为 PR 正文模板：

- 源码位置、2000 行上限与构建登记符合项目规范。
- 调试代码仅在调试构建生效。
- 设置声明、保存和读取同步；界面订阅绑定生命周期。
- 界面与会话数据在主线程处理，错误按返回值表达。
- 注释简短，说明意图和约束。
- fork 子模块的改动已推送到 fork 仓库，主仓库指针指向已推送的提交。
- 提交范围清楚，界面改动有实际截图，构建与测试结果可追溯。
- 在内部记录中区分实测结果和源码检查，保证对外描述与最终行为一致。

一个请求围绕一个主题；跨层或涉及大量文件时说明必要性。
准备好可审查的结果后，再按用户授权创建请求或推送。
